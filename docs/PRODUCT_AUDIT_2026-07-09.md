# JZone 私人音乐 App 项目审查 2026-07-09

## 审查原则

这份审查不按聊天上下文复述任务，而是从仓库当前事实出发：

1. 先看产品对象是否清晰：歌曲、专辑、歌单、评论、用户、播放记录。
2. 再看核心用户路径是否闭环：上传、编辑、保存、播放、收藏、评论、归类。
3. 再看页面边界是否合理：现在就听、资料库、创作、我的、播放页分别解决什么问题。
4. 最后看工程结构是否支撑继续迭代：数据层、状态层、组件层、样式层是否有清晰边界。

以后做夜间审查时，默认按这个标准执行，不再只做“已改动验收”。

## 当前产品判断

JZone 现在已经不是一个简单播放器，而是一个小范围私人音乐资料库。它的核心价值应该是：

- 把自己和小范围成员上传的录音稳定保存下来。
- 让用户能用专辑、歌单、收藏、评论、记忆卡片整理内容。
- 让用户很快回到最近听、常听、自己上传、自己收藏的内容。
- 让上传者能管理作品，普通用户能浏览和互动。

所以后续优化不应该继续只围绕单个按钮，而应该围绕“音乐对象管理”和“私人资料库工作流”来做。

## P0：上传应升级为后台任务流

代码依据：

- `components/upload/useUploadDraft.ts:74` 同时管理草稿、文件快照、预览、转码、封面、恢复。
- `components/upload/useUploadDraft.ts:292` 文件选择后立即进入解析、持久化、标签读取和预览状态。
- `components/upload/useUploadDraft.ts:387` 转码逻辑仍在上传编辑 hook 内部。
- `components/upload/useUploadSave.ts:11` 保存逻辑又负责 Supabase/COS 上传、本地兜底、关联专辑歌单和提示。

产品问题：

上传是这个项目最关键的生产流程，但现在它还是“页面内表单状态”。用户一旦切页、浏览器回收文件句柄、IndexedDB 读写延迟、转码加载慢或网络波动，就会感觉流程被打回。

建议方向：

- 新增全局 `UploadQueue` / `UploadTask` 模型，上传不再属于某个页面组件。
- 文件选择后创建任务：`selected -> analyzing -> ready -> transcoding -> uploading -> saved -> failed`。
- 创作页只负责展示和编辑当前任务，切到其他页面任务继续存在。
- 所有失败都落在任务上，用户可以重试、重新选择文件、放弃草稿。
- M4A/无后缀文件先通过探测得到 MIME、扩展名和预览能力，再决定是否转码。

验收标准：

- 第一次选择 M4A、MP3、无后缀音频都不会被打回上传入口。
- 转码加载慢时可以离开创作页，回来仍看到同一个任务。
- 保存成功后歌曲、专辑/歌单关系、播放源三者一致。

## P0：歌曲身份需要统一事实来源

代码依据：

- `types.ts:4` 的 `Song` 里 `artist`、`album` 是字符串。
- `supabaseApi.ts:384` 使用 `album_songs` 维护合集关系。
- `supabaseApi.ts:432` 又通过专辑标题同步歌曲到专辑。
- `components/upload/useUploadSave.ts:61` 上传时关联选择的合集，`components/upload/useUploadSave.ts:69` 又按专辑名二次同步。

产品问题：

现在歌曲的“所属专辑”既可能来自 `songs.album` 字符串，也可能来自 `album_songs`。短期能工作，但长期会继续出现：专辑创建了但没歌、歌改了专辑但详情页不同步、同名专辑冲突、协作者/自定义艺人难以索引。

建议方向：

- 明确 `album_songs` 是歌曲归属专辑/歌单的事实来源。
- `songs.album` 只作为展示字段或导入时的原始标签，不作为关系判断。
- 上传保存、编辑歌曲、加入专辑/歌单全部调用同一套关系服务。
- 艺人也先保留 display string，但新增可选 `artistProfileId` / `artistProfiles` 思路，支持“数据库用户 + 自定义艺人”共存。

验收标准：

- 在歌曲编辑页改专辑后，专辑详情页立刻能看到这首歌。
- 在加入专辑弹窗中加入歌曲后，歌曲详情/列表显示一致。
- 当前用户改昵称后，新上传默认艺人使用 profile 昵称，不回退到邮箱。

## P1：资料库应成为“可见内容中心”

代码依据：

- `pages/Library.tsx:15` 已有歌曲、专辑、歌单三类内容。
- `pages/Library.tsx:207` 过滤逻辑分散在页面内。
- `pages/Library.tsx:287` 后续 UI 把搜索、筛选、列表、bento、创建入口放在同一页。

产品判断：

资料库不应该只是列表，也不应该和创作页抢“我的上传”。它应该回答一个问题：当前用户能看见什么音乐内容，以及如何快速筛选、归类、进入详情。

建议方向：

- 保留 bento，不改动。
- 列表视图重做为“内容中心”：顶部搜索，下面是歌曲/专辑/歌单分段，筛选变成更清晰的可见性和归属筛选。
- 加入“未归类歌曲”“最近加入”“公开内容”“我的私有”这类智能分组。
- 删除或弱化资料库里的上传弹窗入口，上传职责回到创作工作台。

验收标准：

- 用户能在资料库明确知道自己当前看的是“全部可见”“我的”“公开”“私有”“收藏”。
- 专辑和歌单的空状态能引导用户创建或添加歌曲。
- 不影响当前 bento 视图。

## P1：创作页应成为“作品工作台”

代码依据：

- `pages/Upload.tsx:21` 创作页现在已统计我的上传、私有数量、空间。
- `pages/Upload.tsx:75` 上传编辑器和我的上传列表放在同一页。
- `pages/Upload.tsx:100` 我的上传列表复用歌曲操作菜单。

产品判断：

创作页的价值不是“选择文件”本身，而是管理我创建/上传的内容。它应该像一个个人作品工作台。

建议方向：

- 顶部保留作品数量、私有、空间，但加上真实状态：草稿数、失败任务数、待处理任务。
- 上传编辑器改为任务卡片：当前任务、历史草稿、失败重试。
- 我的上传列表增加“未归类”“私有”“公开”“最近修改”。
- 后续作品表现统计放这里：播放、收藏、评论。

验收标准：

- 用户上传失败后能在创作页看到失败原因和重试入口。
- 用户能一眼区分已发布作品、私有草稿、待处理音频。
- 创作页不再因为切页或刷新丢失正在处理的任务。

## P1：现在就听应更像私人音乐入口，而不是展示橱窗

代码依据：

- `pages/Home.tsx:80` 最近播放是本地 recent ids。
- `pages/Home.tsx:211` 最新公开直接从当前歌曲列表切片。

产品判断：

现在就听不需要堆很多大封面。它应该服务“立刻继续”和“今天值得听”。

建议方向：

- 保持“最新公开”大封面视觉。
- 最近播放继续走效率卡，但后续应接后端或至少带时间戳，避免多设备不同步。
- 增加轻量入口，不急着做完整页面：最近常听、我的收藏前几首、最近有人评论的歌。
- 不放“我的上传”，避免和创作页重复。

验收标准：

- 打开首页 3 秒内能继续播放上次内容。
- 首页只放少量高价值入口，不再成为所有功能的集合页。

## P1：播放页需要成为歌曲对象的中心页

代码依据：

- `pages/PlayerView.tsx:20` 播放页已经持有评论、记忆卡片、队列、收藏和更多菜单。
- `pages/PlayerView.tsx:122` 歌曲信息只显示 title/artist。
- `components/UniversalContextMenu.tsx:117` 更多菜单已有加入歌单、收藏、编辑、公开私有、置顶、删除。

产品判断：

播放页现在播放体验不错，但“这首歌是什么、属于哪里、谁收录的、我能怎么整理它”还不够强。私人音乐库里，播放页应该是歌曲对象中心。

建议方向：

- 歌曲信息区增加轻量元信息：所属专辑、收录者、可见性、我的播放次数。
- 更多菜单里的文案继续对象化，例如“置顶此歌曲到我的上传”。
- 队列可以保留当前简洁模式，但需要支持拖拽排序或至少上移/下移。
- 评论后续做回复之前，先保证评论定位、头像、时间点跳转足够稳定。

验收标准：

- 用户在播放页能直接判断这首歌属于哪个专辑/歌单，以及是谁上传/收录。
- 用户能从播放页完成收藏、加入合集、编辑元信息、打开评论。

## P1：个人页需要拆成展示页和设置页

代码依据：

- `pages/Profile.tsx:167` 之后同时管理 profile 缓存、合集、设置、背景、头像框、液态玻璃参数、菜单。
- `pages/Profile.tsx:493` 和 `pages/Profile.tsx:529` 存在两段相似的头像/封面签名 URL 解析逻辑。
- `pages/Profile.tsx:1175` 液态玻璃参数设置也放在个人页设置里。

产品判断：

个人页现在承载太多：个人展示、作品/收藏、背景管理、头像框、状态、全局玻璃参数。作为私人音乐 app，“我的”应该优先展示我和音乐的关系，而不是变成全局设置面板。

建议方向：

- 个人展示页：头像、背景、状态、作品、收藏、听歌统计。
- 设置页/设置抽屉：账号资料、背景、头像框、视觉参数、PWA/缓存。
- 全局视觉参数从个人页中拆成 `AppearanceSettings`，以后可复用。

验收标准：

- 普通查看个人页时不被设置项干扰。
- 设置打开后可清晰找到账号、外观、数据/缓存。
- Profile 文件拆分后单文件不再超过 500 行。

## P2：工程简化任务

### 拆分数据层

代码依据：`supabaseApi.ts:247` 到 `supabaseApi.ts:851` 同时包含合集、歌曲、评论、收藏、播放统计、文件签名、上传、个人资料。

建议拆分：

- `songsApi.ts`
- `collectionsApi.ts`
- `commentsApi.ts`
- `profilesApi.ts`
- `storageApi.ts`
- `statsApi.ts`

收益：

- 降低修改一个功能影响全局的概率。
- 让上传、播放、资料库各自依赖更明确。

### 拆分应用壳

代码依据：`App.tsx:25` 内含底部导航，`App.tsx:350` 内含全屏策略，`App.tsx:389` 内含主布局和路由。

建议拆分：

- `AppShell`
- `BottomNavigation`
- `useAutoFullscreen`
- `useAppRoute`
- `MiniPlayerLayer`

收益：

- 导航动画、PWA、全屏、路由互不干扰。

### 统一反馈系统

代码依据：`rg` 扫描发现多个 `alert()` / `confirm()` 分布在资料库、个人页、详情页、菜单、上传保存、播放器状态中。

建议方向：

- 新增全局 `ToastProvider` 和 `ConfirmDialog`。
- 成功/失败/部分成功都用统一视觉反馈。
- 删除保存成功后的阻塞式 `alert`。

收益：

- 移动端体验更接近原生。
- 避免 alert 打断音频播放或输入法状态。

### 清理样式层

代码依据：`index.css` 1505 行，包含底部 tab、F 方案、毛玻璃、菜单、登录、实验样式和全局动画。

建议方向：

- 抽出 `styles/glass.css`、`styles/navigation.css`、`styles/auth.css`、`styles/animations.css`。
- 实验 lab 样式独立到 lab 页面或删除未使用类。
- 保留当前底部 tab 方案，不继续在主程序堆实验代码。

收益：

- 之后调整毛玻璃/液态玻璃不会影响播放器、登录、菜单多个区域。

## P2：测试策略应换成真实流程测试

当前 `npm run typecheck` 通过，但这只能证明类型没有明显错误。

后续应补的测试不是重复点 tab，而是这些真实路径：

1. 上传路径：选择 M4A/无后缀文件 -> 进入编辑 -> 预览播放/暂停 -> 保存 -> 播放保存后的歌曲。
2. 关系路径：编辑歌曲专辑 -> 专辑详情页出现歌曲 -> 从专辑移除/重新加入。
3. 播放路径：播放公开歌 -> 打开播放页 -> 收藏 -> 加入歌单 -> 评论 -> 队列切换。
4. 菜单路径：长按不同位置的歌曲 -> 菜单不被遮挡 -> 内容可读 -> 操作后有非阻塞反馈。
5. PWA 路径：已安装模式、浏览器模式、局域网模式分别验证安全区、全屏、上传文件选择。

## 推荐的下一阶段任务排序

1. P0 上传任务流重构：先解决最核心的生产流程稳定性。
2. P0 歌曲-专辑-歌单关系服务统一：避免保存、编辑、加入合集继续分裂。
3. P1 全局反馈系统：替换 alert/confirm，提升所有操作的可信度。
4. P1 创作页工作台化：围绕上传任务、我的作品、失败重试、作品状态重做信息结构。
5. P1 播放页歌曲对象信息增强：补专辑、收录者、可见性、我的播放次数。
6. P1 资料库列表视图 PRD：保留 bento，只重做列表视图的信息架构。
7. P2 Profile 拆分和设置独立：降低个人页复杂度。
8. P2 数据层和样式层拆分：为后续长期迭代清理边界。
