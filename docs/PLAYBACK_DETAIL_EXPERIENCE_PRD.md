# 播放与详情体验优化 PRD 草案

## 背景

上一阶段已经完成资料库、创作工作台、可见性权限和现在就听的数据化整理。当前项目的主要问题不再是“功能入口是否存在”，而是用户在真实听歌过程中会遇到若干体验断点：

- 播放详情页能收藏、评论、打开更多菜单，但缺少“把当前歌曲加入某个歌单或专辑”的核心收纳动作。
- 歌曲、歌单、专辑的更多菜单已经具备编辑、置顶、公开/私有等能力，但部分文案缺少对象语义，例如“置顶”容易被误解为页面置顶或系统异常。
- 加载、保存、加入合集、评论提交等异步过程的反馈还不够 Apple 风格，用户会感觉“点了但不知道发生了什么”。
- 播放页、歌单/专辑详情、资料库列表、创作页、个人页之间已有部分相似能力，但尚未抽成一致的交互语言。

本 PRD 用于讨论播放页与核心详情体验的一期优化。敲定后再生成 tasks。

## 产品目标

- 让“听到一首歌 → 收藏 / 加入歌单 / 加入专辑 / 分享 / 查看评论”的路径完整闭环。
- 让所有更多菜单的动作文案都能明确说明作用对象，避免用户误解。
- 能复用的选择器、菜单、骨架屏、反馈组件优先复用；发现重复逻辑时优先抽成小组件，而不是继续在页面里复制。
- 用 Apple Music / Apple Design 的方式强化核心体验：内容优先、强媒体焦点、清晰层级、克制动效、明确反馈。
- 为加载、保存、加入、评论等等待状态建立统一骨架屏和过渡规范。
- 不改变资料库 bento 视图，不做商业化、推荐算法、复杂社交系统。

## 非目标

- 不在本阶段重做音频播放内核。
- 不在本阶段实现 MV、复杂歌词动效、评论回复树、头像框系统。
- 不重做资料库 bento 画布。
- 不引入商业化、运营后台、审核流。
- 不处理安全专项，例如 RLS 以外的完整安全审计。

## 当前代码事实

- `pages/PlayerView.tsx` 播放页已有收藏按钮、更多按钮、评论入口、记忆卡片入口、待播清单入口。
- 播放页更多按钮复用 `components/UniversalContextMenu.tsx`。
- `UniversalContextMenu` 当前歌曲动作包括：分享、编辑信息、设为私有/公开、置顶/取消置顶、删除、收藏/取消收藏。
- `UniversalContextMenu` 当前缺少“加入专辑 / 歌单”。
- `pages/Upload.tsx` 的“我的上传”列表已有“加入专辑 / 歌单”能力，使用 `CollectionCreatableSelect` 和 `attachUploadedSongToCollection`。
- `components/CollectionContextMenu.tsx` 合集菜单当前包含“搜索、置顶、编辑信息、设为公开/私有、删除”，其中“置顶/取消置顶”缺少对象说明。
- `pages/CollectionDetailPage.tsx` 已有向合集添加歌曲的入口和 `SongPickerModal`。
- `components/CommentsSheet.tsx` 评论目前使用本地 store 新增评论，头像和昵称来自前端临时值，仍需和后端评论模型进一步核对。

## 核心用户场景

### 场景 1：正在播放时收纳当前歌曲

用户在播放详情页听到一首歌，想把它加入某个歌单或专辑。用户点击更多按钮，选择“加入歌单或专辑”，弹出选择器，可以搜索已有歌单/专辑，也可以新建后加入。完成后出现明确成功反馈，并且对应合集详情页能看到这首歌。

### 场景 2：资料库或个人页中收纳歌曲

用户在资料库、个人页收藏列表、现在就听大封面卡中发现歌曲，也应该能通过相同的更多菜单完成“加入歌单或专辑”。同一个动作不应只出现在创作页。

### 场景 3：管理歌单或专辑

用户打开歌单或专辑右上角更多菜单，看到动作文案时应该立即明白作用对象。例如“置顶此歌单”“取消置顶此专辑”“编辑歌单信息”“删除此专辑”，而不是孤立的“置顶”“删除”。

### 场景 4：等待状态

用户打开播放页、歌单详情、评论区、个人页合集列表或执行加入操作时，应看到与页面结构一致的骨架屏或过渡反馈，而不是空白、突兀刷新或无感等待。

## 功能需求

### 1. 播放页更多菜单补齐收纳动作

优先级：P0

播放页当前歌曲的更多菜单新增：

- “加入歌单或专辑”
- 入口位置建议放在“分享”之后、“编辑信息”之前。
- 所有人可见歌曲都可以加入自己的歌单。
- 专辑允许收录其他用户的可见歌曲，以支持合唱者、翻唱/独唱收录、多人协作专辑等场景。
- 歌单和专辑的可加入范围都以“当前用户可见歌曲 + 当前用户拥有或可编辑的目标合集”为基础。

交互要求：

- 点击后打开统一的 `CollectionCreatableSelect` 风格弹窗。
- 支持搜索已有歌单/专辑。
- 支持在弹窗中新建歌单或专辑。
- 加入中按钮进入 loading 状态，禁止重复提交。
- 成功后使用轻量 toast 或底部反馈，不使用 `alert`。
- 失败时说明原因，例如“这首歌已经在该歌单中”或“没有权限加入专辑”。

### 2. 通用歌曲菜单能力补通

优先级：P0

同一个 `UniversalContextMenu` 应成为所有歌曲场景的通用能力层。凡是页面使用歌曲更多菜单，都应具备一致动作：

- 分享
- 加入歌单或专辑
- 收藏 / 取消收藏
- 编辑信息，仅歌曲所有者可见
- 设为公开 / 设为私有，仅歌曲所有者可见
- 置顶此歌曲 / 取消置顶此歌曲，仅歌曲所有者可见
- 删除此歌曲，仅歌曲所有者可见

说明：

- 现在就听的大卡片可以先不显示更多按钮，但长按或后续二级入口应复用同一菜单。
- 资料库列表、创作页“我的上传”、个人页歌曲列表应逐步统一到同一菜单。
- 现有创作页的 `CollectionCreatableSelect` 和 `attachUploadedSongToCollection` 应作为加入合集能力的基础，不重新写一套选择器和保存逻辑。
- 菜单动作排序要遵循“常用、安全、危险”顺序，删除永远放底部并使用红色。

### 3. 歌单 / 专辑菜单文案优化

优先级：P0

合集菜单中的动作要带对象语义：

- 歌单：
  - 搜索此歌单
  - 置顶此歌单 / 取消置顶此歌单
  - 编辑歌单信息
  - 设为公开歌单 / 设为私有歌单
  - 删除此歌单
- 专辑：
  - 搜索此专辑
  - 置顶此专辑 / 取消置顶此专辑
  - 编辑专辑信息
  - 设为公开专辑 / 设为私有专辑
  - 删除此专辑

文案原则：

- 动词要说明作用对象。
- 危险动作必须明确不可恢复。
- 不使用模糊词，例如单独的“置顶”“删除”“编辑”。
- 菜单打开时不应让用户怀疑是 bug。

### 4. 歌单 / 专辑详情页体验补齐

优先级：P1

详情页应围绕“大封面、大标题、强媒体焦点”继续优化：

- 保持现有大封面和 Apple Music 风格，不缩小主视觉。
- 公开/私有状态应在标题区有轻量标识。
- 右上更多按钮与标题区操作按钮语义一致。
- 添加歌曲成功后，在歌曲列表顶部插入对应数量的骨架行，直到真实数据刷新完成。
- 如果合集为空，空状态应给出清晰动作：
  - 专辑：添加我的上传
  - 歌单：添加歌曲
- 从播放页加入某歌单后，进入该歌单应能看到新增歌曲。

### 5. 评论区一期整理

优先级：P1

本阶段不做完整社交系统，但要修复基础断点：

- 核查评论是否已经连接后端。
- 评论提交后再次打开评论区不应丢失。
- 评论头像和昵称应来自用户 profile 或 QQ 邮箱默认头像策略，而不是临时随机头像。
- 点赞按钮一期可先实现单用户本地/后端去重逻辑，后续再扩展。
- 评论输入区继续保留当前键盘避让逻辑，避免不同手机浏览器中输入框被遮挡。

### 6. 加载骨架屏与等待反馈

优先级：P1

需要统一骨架屏，而不是每个页面随意写空状态：

- 播放页：
  - 封面加载前使用正方形封面骨架。
  - 标题区使用两行文本骨架。
  - 进度条在音频 metadata 未就绪时显示静态轨道。
- 歌单 / 专辑详情：
  - 大封面骨架。
  - 标题、作者、按钮区骨架。
  - 歌曲列表骨架行。
- 评论区：
  - 打开 sheet 后先显示 3-5 条评论骨架。
  - 提交中显示发送按钮 loading。
- 创作页：
  - 上传保存时继续使用列表骨架，但需要升级为和真实歌曲行尺寸完全一致。
  - 封面上传/头像上传成功前使用模糊化或流光过渡。
- 个人页：
  - 头像、封面、合集列表使用局部骨架。

Apple 风格要求：

- 骨架屏要模拟真实布局，不做通用大灰块。
- 骨架屏应抽成可复用组件，例如封面骨架、歌曲行骨架、合集头部骨架、评论行骨架，避免各页面重复写不同尺寸的占位。
- 使用低对比度、缓慢流光，不要强闪烁。
- 动效持续时间控制在 150-300ms 的进入/退出过渡，骨架流光可以更慢。
- 页面不应因数据回来发生明显跳动。

### 7. 全局交互文案规范

优先级：P1

建立动作命名规则：

- 歌曲对象：此歌曲
- 歌单对象：此歌单
- 专辑对象：此专辑
- 公开/私有：设为公开歌曲、设为私有歌单等，必要时带对象。
- 收藏：收藏此歌曲 / 取消收藏此歌曲。
- 加入：加入歌单或专辑；在确认按钮中使用“确认加入”。
- 删除：删除此歌曲 / 删除此歌单 / 删除此专辑。

建立反馈命名规则：

- 成功：已加入歌单、已设为私有、已置顶此歌单。
- 失败：加入失败，请稍后重试；无权限修改此专辑。
- 加载：加入中、保存中、评论发送中。

## 信息架构建议

### 播放页底部功能栏

当前底部是评论、记忆卡片、待播清单。建议保持三按钮，不再额外塞“加入”按钮，避免破坏播放页的安静感。

“加入歌单或专辑”放入右上更多菜单更合理，因为它属于二级管理动作。

### 歌曲更多菜单

推荐顺序：

1. 分享此歌曲
2. 加入歌单或专辑
3. 收藏此歌曲 / 取消收藏此歌曲
4. 编辑歌曲信息
5. 设为公开歌曲 / 设为私有歌曲
6. 置顶此歌曲 / 取消置顶此歌曲
7. 删除此歌曲

其中 4-7 仅所有者可见，删除底部隔离。

### 歌单 / 专辑更多菜单

推荐顺序：

1. 搜索此歌单 / 搜索此专辑
2. 置顶此歌单 / 置顶此专辑
3. 编辑歌单信息 / 编辑专辑信息
4. 设为公开歌单 / 设为私有歌单
5. 删除此歌单 / 删除此专辑

## 视觉与交互指导

- 播放页继续保留沉浸式封面背景、中心大封面、大标题和 Apple Music 式的黑底层级。
- 不新增密集小列表，不把播放页做成工具页。
- 弹窗使用毛玻璃、圆角、底部 sheet 或居中 modal，触控区不低于 44px。
- 成功反馈优先使用 toast / inline feedback，不使用浏览器 `alert`。
- 所有图标按钮需要 `aria-label`。
- 所有异步按钮 loading 时禁用重复点击。
- 菜单打开、sheet 展开、骨架替换真实内容要使用克制的 opacity / transform 动效。

## 数据与权限原则

- 加入歌单：当前用户可将可见歌曲加入自己创建的歌单。
- 加入专辑：当前用户可将可见歌曲加入自己创建或可编辑的专辑，以支持合唱者和多人协作收录场景。
- 修改歌曲公开/私有、置顶、删除：仅歌曲所有者。
- 修改歌单/专辑公开/私有、置顶、删除：仅合集创建者。
- 评论：应以当前登录用户 id 为准写入后端，并读取 profile 昵称和头像。

## 验收标准

- [ ] 播放页更多菜单出现“加入歌单或专辑”。
- [ ] 当前歌曲能加入已有歌单，并在歌单详情页刷新后可见。
- [ ] 当前歌曲能新建歌单并加入。
- [ ] 专辑允许加入其他用户的可见歌曲，并在权限不足时给出清晰提示。
- [ ] 资料库、创作页、个人页中歌曲更多菜单的动作语义一致。
- [ ] 合集菜单不再出现孤立的“置顶/删除”等模糊文案。
- [ ] 加入、保存、评论发送等异步操作有 loading 状态，且不能重复提交。
- [ ] 播放页、歌单/专辑详情、评论区至少具备结构化骨架屏。
- [ ] `npm run check` 通过。
- [ ] `npm run smoke:auth` 通过。
- [ ] 手机局域网实机验证核心流程：播放页加入歌单、歌单详情查看新增歌曲、菜单文案无歧义。

4. 评论点赞是否放入本次一期？当前推荐是放入 P1，但评论回复、头像框显示延后。
