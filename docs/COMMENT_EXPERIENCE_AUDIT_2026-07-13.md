# 评论体验审查（2026-07-13）

## 产品定位

评论区服务于小范围熟人之间围绕歌曲和具体播放时刻交流。视觉与动效遵循 Apple 式克制和可读性，社区能力参考成熟音乐社区，但不引入热榜运营、商业推荐和复杂审核后台。

## 当前已经完成

- 评论已接入 Supabase，受歌曲可见性 RLS 约束。
- 昵称和头像按用户 ID 读取最新资料，不再把注册邮箱名当作稳定身份。
- 支持绑定播放时间点并一键跳转。
- 支持单用户一次点赞，前端采用乐观更新并在失败时回滚。
- 支持移动端软键盘视窗避让。
- 发送采用乐观插入；本轮补上失败回滚和明确错误反馈。
- 本轮修复歌曲后台刷新误清空当前评论的问题。

## P0：可靠性闭环

- [x] 后台歌曲刷新不得清空已经打开的评论列表。
- [x] 评论发送失败时移除失败的乐观评论并提示用户。
- [ ] 为每首歌曲建立短期 SWR 评论缓存，切回歌曲时先显示缓存再静默刷新。
- [x] 评论拉取失败显示重试状态，不能把网络失败表现成“暂无评论”。
- [x] 页面从后台恢复或网络重连后，仅刷新当前歌曲评论。
- [x] 评论数量较多时改为分页加载，避免一次查询全部评论和点赞记录。

## P1：符合直觉的核心互动

- [x] 支持回复评论，先做单层回复；数据使用 `parent_comment_id`，不做无限嵌套。
- [x] 用户可删除自己的评论，歌曲所有者可管理自己歌曲下的评论。
- [x] 评论展示头像挂件，与个人页身份表达保持一致。
- [x] 支持“最新 / 最多赞”两种排序，默认仍为最新。
- [x] 超过五行的长评论折叠，展开后保持当前滚动位置。
- [x] 分享评论时生成 1080×1350 PNG，并优先调用系统文件分享。

## P2：可选增强

- [ ] 回复提醒采用应用内轻量入口，不建设完整通知中心。
- [ ] 支持 `@用户`，选择对象时绑定用户 ID，显示名允许后续变化。
- [ ] 歌词页完成后，评论可选择绑定歌曲时间或歌词行。
- [ ] 对小范围使用场景保留举报/屏蔽的数据接口，但暂不增加显眼入口。

## 推荐实施顺序

1. 完成评论 SWR、错误重试、恢复刷新和分页，先保证数据永远可信。
2. 增加单层回复、删除权限和头像挂件，形成完整交流闭环。
3. 增加排序、长文折叠和评论分享，提升高评论量时的使用效率。
4. 等歌词页和通知方向确定后，再接入歌词锚点与回复提醒。
