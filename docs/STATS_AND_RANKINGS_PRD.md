## 1. 背景、意图与成功结果

### 1.1 用户真正要完成的事

用户希望知道自己反复听哪些歌，并能从“我的”页快速回到这些歌曲；创作者希望以后能看到自己的作品表现；小范围用户以后可以浏览公开歌曲的全站排行。统计必须可信、可解释、不泄露私有内容，也不能让排行需求破坏现有播放和 Bento 资料库体验。

### 1.2 产品成功结果

在口径获批且完成第一期后：

1. 登录用户能在“我的”查看本人的本周、本月、全部时间个人听歌排行。
2. 同一有效播放只计一次；暂停继续、刷新、重连或换设备不会制造重复记录。
3. 私有歌曲只对拥有者可见；任何个人统计都不能被另一个账号读取。
4. 没有数据、数据过旧、查询失败和迁移缺失时均有诚实状态，不把失败伪装成 0 次播放。
5. “现在就听”只承载少量可播放入口；资料库的 Bento 视觉和交互不被排行改造。
6. 全站公开排行与创作者作品表现在第一期只保留接口边界，不进入实现验收。

## 2. 范围与非目标

### 2.1 第一期范围：个人排行

第一期唯一完整实现对象是**个人听歌排行**：

- 数据主体：当前登录用户自己的有效播放记录。
- 页面主体：`我的`，在现有个人页内承载完整排行，不新增一级页面。
- 时间筛选：本周、本月、全部时间；时间定义见第 5 节。
- 第一期指标：建议只做 `qualified_play_count`（有效播放次数），计数门槛按 D1 已批准口径执行。
- 首页入口：允许作为独立的轻量子批次，只展示前 3–5 首并回到“我的”；是否随第一期打开需单独确认。

### 2.2 只定义接口边界、不在第一期实现

| 产品位置 | 产品责任 | 第一期状态 |
| --- | --- | --- |
| 我的 | 个人听歌统计与个人排行 | 实现范围 |
| 资料库 | 公开歌曲全站榜 | 只定义公开排行接口，不加 UI |
| 创作 | 我的作品播放、收藏、评论表现 | 只定义创作者接口，不加 UI |
| 现在就听 | 轻量排行入口和快速播放 | 只允许前 3–5 首入口；完整统计不放这里 |

### 2.3 明确不做

- 不在本轮实现全站排行榜、创作者统计、推荐系统、热榜运营或复杂图表。
- 不把公开排行入口塞进资料库 Bento 画布，不重做 Bento、播放页、评论和液态玻璃。
- 不在本轮修改播放计数实现；D1 已批准以裁剪后有效播放区间的 20% 为主阈值，当前最少 1 秒规则继续保留，短录音完整播放兜底和单会话去重见第 4 节。
- 不回填、重算、猜测迁移前的周/月播放数据。
- 不公开个人播放次数、听歌历史、设备信息、评论者身份或私有歌曲元数据。
- 不通过旧的 `updated_at` 伪造播放事件时间。

| 个人 RPC 安全 | `increment_user_song_play` 检查登录态并按 `(user_id, song_id)` 累加（`supabase/sql/011_user_song_plays.sql:37-59`），但函数体本身没有像歌曲总计 RPC 那样再次校验歌曲公开性或拥有者。 | 当前播放器通常只对已加载歌曲调用，但不能把客户端可见性当作服务端安全边界；第一期服务端接口必须由 `auth.uid()`、歌曲可见性和拥有权共同校验。 |

### 3.3 删除、收藏与评论

- **已核实事实**：当前 `deleteSong` 由歌曲拥有者执行删除，先从 `songs` 删除，再清理音频/封面对象（`services/supabase/songs.ts:202-234`）；`user_song_plays.song_id` 对歌曲使用 `on delete cascade`（`supabase/sql/011_user_song_plays.sql:1-6`）。当前歌曲模型没有 `deleted_at` 或 `is_deleted` 字段。
- **已核实事实**：收藏关系存在并以 `(user_id, song_id)` 约束唯一；评论存在 `created_at`，新版评论另有 `deleted_at`/`likes_count` 兼容逻辑，但当前目标页面没有把收藏或评论聚合成排行。
- **推断/缺口**：现有删除是硬删除；歌曲删除后个人播放聚合会随外键级联消失，无法保留可展示的历史排行行。收藏/评论虽有明细表，但没有供创作者或公共排行直接使用的受控聚合接口。

## 4. 计数指标与 D1 已批准口径

### 4.1 历史冲突与已批准口径

历史资料曾记录两种计数口径；以下结论已由用户于 2026-08-26 确认，后续以此为唯一口径：

1. `docs/PROJECT_MEMO.md:26、33、47` 曾记录“单次播放达到 30 秒后才计数、同一播放会话只计一次”，并将其写入过验收描述；这是历史冲突背景，不是当前计数门槛。
2. 同一备忘录后续 `docs/PROJECT_MEMO.md:55` 又记录“20% 播放计数”；该方向与当前批准口径一致。
3. 当前 `store.tsx:57-68` 的真实代码使用有效播放区间的 20%，最少 1 秒；例如有效区间 240 秒时，代码计算的门槛为 48 秒。

因此 D1（已批准，2026-08-26）统一为：**20% 是主阈值，裁剪歌曲按裁剪后的有效播放区间计算；当前最少 1 秒规则继续保留，即数值门槛为 `max(1 秒， 有效播放区间 × 20%)`。不足 30 秒的短录音播放到结尾是兜底语义，不要求必须等到结尾才计数；达到上述数值门槛即可计数。若同一播放会话已因主阈值计数，播放结束的兜底路径不再产生第二次计数。**

### 4.2 指标定义草案

| 指标 | 第一期建议 | 说明 |
| --- | --- | --- |
| `qualified_play_count` | 使用个人排行唯一主指标，按 D1 已批准门槛计数 | 一个通过已批准计数规则的播放事件记 1 次；不等于点击播放、进入播放页、播放列表启动或播放秒数。 |
| `songs.plays_count` | 保留为现有歌曲累计总计 | 继续兼容现有页面和旧数据；第一期不把它直接当作周/月个人排行或公共排行的唯一数据源。 |
| 收藏数 | 第一阶段不入个人排行 | 收藏是关系状态，不是听歌次数；后续作品表现接口可定义。 |
| 评论数/评论点赞 | 第一阶段不入个人排行 | 后续创作者表现可按审核/删除规则定义；不在本轮增加评论聚合。 |
| 独立听众数、听歌时长、完成率 | 不做 | 需要新的事件和隐私决策，不能从当前累计表推导。 |

### 4.3 当前基线与目标契约

当前内存 `counted` 只能保证单个页面播放器实例内的一次性。第一期目标契约应改为服务端可验证的播放事件：

- 每次开始一个可区分的播放会话生成 `play_session_id`，达到门槛后生成唯一 `event_id`。
- 服务端从登录令牌取得 `user_id`，不信任客户端传入的用户 ID。
- 服务端以唯一键/幂等约束接受同一事件一次；同一用户在两个设备上主动开始两个不同会话，建议视为两个合法事件，是否如此计数待确认。
- 暂停继续沿用原会话；跳转不能凭空补足门槛；网络重试必须复用原 `event_id`，不能重新生成。
- 新 RPC/接口必须原子完成“验证歌曲可见性/拥有权、去重、写入事件、更新兼容聚合”的动作；失败返回可区分错误，客户端不能先把失败当成功。

## 5. 本周、本月、全部时间口径

以下是实现草案，**时区、周起始日和离线事件归属仍需用户确认**。所有窗口建议使用半开区间 `[start, end)`，避免跨边界重复计数。

| 窗口 | 建议定义（待确认） | 边界示例 |
| --- | --- | --- |
| 本周 | 产品固定时区中的周一 00:00 至当前时刻；周一 00:00:00 计入新周，前一周周日 23:59:59 归入旧周。 | 不按设备本地时区分别计算，避免同一账号多设备看到不同结果。 |
| 本月 | 产品固定时区中当月 1 日 00:00 至当前时刻；月初边界按同一时区计算。 | 月末最后一秒属于当月，下一月 1 日 00:00 起进入新月。 |
| 全部时间 | 所有被服务端接受且符合当前计数规则的有效播放事件；迁移前只有累计聚合时，显示数据覆盖说明。 | 不用聚合行 `updated_at` 过滤历史窗口；它只能作为并列排序的弱回退字段。 |

### 5.1 时区建议

- **建议**：第一期固定使用 `Asia/Shanghai` 作为产品统计时区；数据库继续使用 UTC `timestamptz` 保存时间，接口返回窗口的 `timezone`、`start`、`end`。
- **替代方案**：按用户偏好或设备时区计算。代价是同一账号跨设备窗口不一致、缓存键更复杂、边界验收更难。
- **待用户确认**：固定 `Asia/Shanghai` 还是用户时区；周一是否为一周起点；离线播放按“实际播放时间”还是“服务端重连接收时间”归属窗口。

### 5.2 旧数据覆盖

- `user_song_plays.plays_count` 可以作为全部时间的历史累计基线，但没有迁移前的每次事件时间。
- 本周/本月不能从 `plays_count + updated_at` 反推；没有事件数据时应显示“该窗口暂无可用数据”或“仅有历史累计”，不估算。
- 不做自动回填、不把歌曲总播放量倒灌成个人播放、不把旧的最近播放 ID 当作有效播放事件。

## 6. 私有歌曲、公开排行与已删除歌曲规则

### 6.1 私人排行

- 仅当前登录用户可读取自己的排行；接口使用 `auth.uid()`，客户端传入的 `userId` 只可用于缓存键，不能作为授权依据。
- 当前用户拥有的私有歌曲可以出现在自己的个人排行中，并显示必要的私有标识；其他用户的私有歌曲不能出现在任何个人排行、首页预览或缓存结果中。
- 查看他人个人页时不显示其个人排行，即使当前歌曲列表能看到该用户的公开作品。

### 6.2 公开歌曲全站榜（后续接口边界）

- 只允许当前仍为 `public` 且通过服务端公开资格校验的歌曲进入公共结果。
- 私有歌曲、仅拥有者可见的歌曲、删除歌曲及其私有播放事件永远不进入公共榜。
- **建议**：歌曲转为私有后立即从公共榜移除；重新公开是否恢复此前公开期间的累计需要单独的数据策略，不能用当前 `songs.plays_count` 猜测。
- 公共接口只返回公开歌曲元数据和聚合值，不返回听众 ID、个人播放次数、设备或原始播放事件。

### 6.3 已删除歌曲

- **当前事实**：歌曲是硬删除，`user_song_plays` 会因外键级联删除；当前没有歌曲软删除字段。
- **建议默认规则**：删除后立即从“我的”、首页、公共榜和创作者表现中隐藏，不显示“已删除歌曲”占位，不将其历史计数迁移到其他歌曲，也不自动恢复。
- 如果产品需要“个人历史仍显示已删除歌曲”或“删除后可恢复”，必须先批准保留策略、匿名快照、恢复语义和新的外键/归档设计；这不属于第一期默认范围。
- 离线队列中的删除歌曲事件由服务端拒绝并从待同步状态移除；客户端不得把它显示为已确认播放。

## 7. 去重、多设备、离线与重连

### 7.1 目标行为

| 场景 | 第一期目标 |
| --- | --- |
| 同一页面暂停/继续 | 同一 `play_session_id`，最多 1 个有效事件。 |
| 快速重复点击 | 不创建重复有效事件；未达到门槛的尝试不计数。 |
| 跳转/拖动进度 | 不把跳过的媒体时间计入有效听歌时长。 |
| 同一事件重试 | 复用 `event_id`，服务端幂等返回同一结果。 |
| 同账号多设备 | 不同主动播放会话分别计数；同一会话跨设备恢复必须复用会话 ID。这个“不同会话是否分别计数”待用户确认。 |
| 断网后继续 | 达到门槛后进入本地待同步队列，不能直接宣称已写入服务端。 |
| 重连 | 按指数退避重试原事件；恢复网络、切换账号、退出登录时重新校验身份和歌曲状态。 |
| 账号切换/退出 | 清空上一账号的排行内存、待同步个人数据和私有缓存；不显示上一账号的排行。 |

### 7.2 离线队列约束

建议只在“有效播放门槛已达成”后入队，队列项至少包含 `event_id`、`play_session_id`、歌曲 ID、客户端观察时间、策略版本和入队时间；服务端以接收时间或批准的事件时间为准。队列需要：

- 每用户隔离，不能被另一账号读取；
- 有上限、重试次数和过期策略；
- 重连后先验证登录态、歌曲是否仍可见、策略版本是否有效；
- 失败分为可重试和不可重试，不用 0 次覆盖旧的已确认数据；
- 不保存原始音频、评论内容、IP 或设备指纹。

**待用户确认**：离线事件计入原始播放发生的窗口，还是计入服务端接收的窗口；离线队列是否保留超过一个统计周期；多设备同时播放如何定义为同一会话。

## 8. 接口边界（第一期只实现个人排行）

下面是逻辑接口草案，不是本轮要创建的 API 或 SQL。

### 8.1 第一期接口：个人听歌排行

建议接口名：`get_my_listening_rankings`。

请求参数：

- `window`: `week | month | all`；
- `metric`: 第一期固定 `qualified_play_count`；
- `limit`: 默认 50，上限 100；
- `cursor`: 可选，供稳定分页使用；
- 时区不由客户端自由覆盖，服务端返回实际采用的时区。

响应至少包含：

- `window`: `key`、`timezone`、`start`、`end`、`is_partial`；
- `rows`: `rank`、`song_id`、标题、艺人、可见封面引用、`qualified_play_count`、`last_qualified_at`（如可用）、`visibility`；
- `data_coverage`: `legacy_aggregate | event_complete | partial | unavailable`；
- `generated_at`、`is_stale`、`next_cursor`；
- 对齐后的 `metric_version`/`count_policy_version`，便于解释 D1 已批准口径（20% 主阈值、最少 1 秒规则和短录音播放结束兜底）。

安全要求：服务端从会话取得当前用户；个人接口不接受任意目标用户 ID，不返回个人播放事件原文，不因前端传入私有歌曲 ID 而扩大权限。

### 8.2 资料库公开歌曲排行（后续，仅接口边界）

建议接口名：`get_public_song_rankings`。

- 输入窗口、指标、分页与策略版本；不含用户 ID。
- 服务端先过滤当前公开歌曲，再聚合公开资格事件。
- 输出只包含公开歌曲展示所需字段与全站聚合次数；不返回私有歌曲数量、隐藏行、听众身份或个人计数。
- 不能直接把现有 `songs.plays_count` 当成周/月公共榜依据；它缺少事件时间和播放时的公开状态。

### 8.3 创作作品表现（后续，仅接口边界）

建议接口名：`get_my_creation_performance`。

- 目标歌曲集合由服务端按当前用户拥有权确定；不信任客户端传入的任意 owner ID。
- 预留 `qualified_play_count`、收藏数、评论数及窗口覆盖信息；第一期不实现收藏/评论聚合。
- 私有作品表现只对作品拥有者可见；公共分享只允许经过批准的公开聚合结果。
- 与个人听歌排行明确区分：这是“别人/全站对我的作品的互动”，不是“我听了哪些歌”。

### 8.4 统一响应状态

所有排行接口应区分：

- `loading`：尚未有结果；
- `ready`：当前窗口有服务端结果；
- `empty`：查询成功但没有符合口径的数据；
- `stale`：展示缓存，同时标明最后成功时间并后台刷新；
- `error`：查询失败，保留可用旧结果但不改写为 0；
- `unavailable`：旧数据库或接口尚未支持，不阻塞播放、浏览和编辑。

- 使用现有黑底、清晰文字层级、轻量列表和少量分隔，不引入 Bento 卡片墙、彩色热榜、复杂图表或大封面统计海报。
- 空状态只回答“为什么为空”和“下一步做什么”：

  - 公开榜/作品表现（未来）：分别使用 `暂无公开排行数据`、`作品有播放后会显示`。
- 加载状态使用稳定的排行行骨架或文本占位，避免整页跳动；缓存结果和刷新状态必须可辨识。

## 10. 数据库迁移草案（只描述，不新建 SQL）

本节是迁移设计说明，**本轮不创建、不执行任何 SQL**。

### 10.1 推荐数据结构方向

1. 新增按事件保存的播放记录概念（名称可在实施前确定），至少包含事件 ID、用户 ID、歌曲 ID、播放会话 ID、服务端接收时间、可选的事件发生时间、策略版本、有效听歌秒数和必要的歌曲状态快照。
2. 对事件 ID，以及“用户 + 播放会话 + 歌曲”的业务组合建立幂等约束；同一合法事件重复提交只能产生一次聚合增量。
3. 为用户/时间、歌曲/时间建立查询索引；查询默认有上限和游标，不允许按全量事件做无界客户端聚合。
4. 让受保护的服务端函数负责权限、去重和聚合；普通客户端不能任意插入有效播放事件。
5. 在公开排行读取侧建立“当前公开歌曲 + 公开资格事件”的受控视图或函数，避免直接暴露原始事件表。

### 10.2 兼容与迁移顺序

- 保留 `songs.plays_count`、`user_song_plays` 和现有 RPC，先以适配层兼容旧客户端；不重命名、不删除、不覆盖现有累计值。
- 新事件写入与兼容累计更新必须在同一幂等事务或可验证的补偿流程中完成，避免事件和累计分叉。
- 全部时间可以读取旧个人累计作为 `legacy_aggregate`；本周/月只使用迁移后有明确时间的事件，除非用户另行批准历史回填。
- 旧数据库缺少新表/函数时，排行入口显示 `unavailable` 或不显示，播放、浏览、编辑继续工作；不通过异常返回伪造零值。
- 迁移前必须先在本地/隔离环境验证两个账号的 RLS、私有歌曲、重复事件、删除歌曲、旧客户端回落和窗口边界；未经用户批准不得远程应用。

### 10.3 删除策略的迁移分支

- 默认分支：沿用硬删除，删除时相关事件/聚合不可再展示；不保留可识别歌曲快照。
- 若用户批准历史保留分支：需要单独设计歌曲墓碑/匿名快照、事件外键策略、恢复规则和保留期限；不能简单把 `on delete cascade` 改掉后直接上线。

## 11. 缓存、刷新与数据新鲜度

- 复用当前个人统计“按用户隔离、缓存优先、约 30 分钟后台刷新”的方向，但一期接口必须返回 `generated_at`、`is_stale` 和覆盖范围。
- 缓存键至少包含用户 ID、窗口、指标版本和时区；退出登录/账号切换立即清除上一账号个人统计与待同步队列。
- 排行查询成功后才更新 canonical cache；乐观播放事件只能标为 `pending`，不得覆盖服务端确认值。
- 首页轻量入口可以复用个人排行响应或独立限量查询，不得为了 3–5 行再拉取完整事件。
- `jzone_recent_song_ids_v1` 当前未按用户隔离；在任何统计实现中应迁移为用户作用域或明确排除其作为排行数据源。该兼容修复需单独进入实现任务，不在本 PRD 中修改。

## 12. 隐私边界

1. 所有个人接口以登录会话为唯一授权来源；RLS 和服务端函数双重限制，不能仅靠前端过滤。
2. 个人排行只返回当前用户自己的聚合；不返回其他账号的个人排名、播放历史、设备和行为时间线。
3. 私有歌曲的标题、艺人、封面路径、播放次数和待同步事件不能进入公共接口、共享缓存、预加载结果或错误日志。
4. 公共排行只返回仍公开的歌曲及全站聚合，不展示“被过滤了多少私有歌曲”。
5. 创作者接口只提供作品聚合，不默认提供听众名单、个人贡献明细或评论原文。
6. 不新增 IP、设备指纹或长期跨设备追踪；`device_id` 如确需用于会话去重，必须是短期、不可用于识别用户的技术标识并另行批准。
7. 日志中禁止记录完整个人排行、私有歌曲标题和原始事件 payload；错误日志只记录可追踪的非敏感错误码。

## 13. 性能预算

这些是第一期实现验收目标；D1 计数口径已批准，涉及其他未批准决策的调整仍需用户批准：

- 个人排行接口默认最多 50 行、硬上限 100 行；使用服务端聚合、索引和游标，不在浏览器拉全量事件。
- 有缓存时进入“我的”首屏在 100ms 内显示可用缓存骨架/结果，不等待网络；后台刷新只允许一次进行中请求。
- 正常网络下排行请求服务端 p95 目标不超过 300ms，端到端首个可见结果 p95 目标不超过 1s；超时显示旧结果/重试状态，不阻塞播放。
- 首页轻量入口每个用户每个窗口只保留一份可复用结果，遵循现有约 30 分钟刷新间隔；不预加载音频正文和大图表资源。
- 页面列表使用稳定高度、懒加载封面和有限行数；统计组件不能让常驻 Mini 播放器、底部 Tab 或 Bento WebGL 增加实例。
- 若查询扫描量、重复请求、内存占用或移动端帧时间超过预算，停止扩批并先优化数据契约/索引。

## 15. 验收标准

### 15.1 个人排行功能验收（未来实现）

- 登录账号 A 能查看本周、本月、全部时间；窗口起止时间和时区在响应/界面上可解释。
- 两个账号互相不能读取个人排行；账号 A 的私有歌曲只在 A 的个人排行出现。
- 计数门槛按 D1 已批准的单一策略执行：裁剪歌曲按有效裁剪区间计算 20% 主阈值，并保留当前最少 1 秒规则；不足 30 秒短录音播放到结尾仅作为兜底，不要求等到结尾才计数，且不会与主阈值重复计数。
- 同一播放会话暂停/继续只计一次；跳转不能刷过门槛；同一 `event_id` 重试只计一次。
- 多设备的不同会话按最终批准规则计数；同一会话重连不会重复。
- 周一、月初、时区跨日样例与半开区间一致；并列名次稳定且可复现。
- 查询成功无记录显示空状态；查询失败不显示 0、不覆盖最后成功结果；旧接口不可用时不影响播放、浏览、编辑。
- 删除歌曲不在任何用户可见排行出现；若未来采用历史保留分支，必须有单独批准和测试证据。
- 首页若打开轻量入口，最多 3–5 条，可直接播放并回到完整个人排行；无数据时隐藏入口或显示克制空状态。
- 资料库 Bento 视图、现有列表排序、拖拽和常驻播放器无回归。

### 15.2 数据与安全验收

- 服务端不接受客户端伪造的 `user_id`、私有歌曲公开资格或有效播放结果。
- 重复请求、并发请求、刷新和重连测试后，服务端事件数与聚合数一致。
- 不存在跨账号缓存命中、公共响应含私有歌曲、错误响应泄露隐藏歌曲数量的情况。
- 数据覆盖标识正确：旧累计不得标记为完整周/月事件数据，未支持迁移不得伪造完成。

### 15.3 性能验收

- 默认/上限行数、游标和索引生效；无全量事件客户端聚合或 N+1 歌曲详情请求。
- 缓存首屏和网络 p95 达到第 13 节目标；弱网下播放控制与底部导航不被统计请求阻塞。
- 关闭功能开关后，旧播放计数、个人缓存和资料库原有行为恢复，不需要回滚破坏性数据。

## 16. 回滚条件与回滚方式

### 16.1 立即停止条件

- D1 已批准的 20% 主阈值、最少 1 秒规则、裁剪区间或短录音兜底与实现/SQL不一致，却已经开始写入实现或 SQL。
- 发现跨账号个人数据、私有歌曲或删除歌曲泄露。
- 服务端聚合与事件幂等不一致，或播放计数与批准的基线不一致。
- 查询超时、缓存串号、离线重试重复计数，或远程写入超出批准范围。
- 资料库 Bento、播放器、播放上下文或现有创作/收藏行为出现回归。

### 16.2 回滚方式

- 首选关闭个人排行/首页预览功能开关，隐藏新入口；保留旧 `songs.plays_count`、`user_song_plays` 和旧客户端播放能力。
- 新事件停止写入后，已存在的旧累计不删除、不重算、不覆盖；修复后再按批准的兼容策略恢复。
- 数据库迁移的回退、历史回填、墓碑清理和任何删除必须另行取得用户批准，不能用前端回滚代替数据库回滚。
